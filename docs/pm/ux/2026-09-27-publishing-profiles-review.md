# Publishing profiles — post-implementation UX review

## 結論

提示されたスクリーンショットとローカルモックでの操作観察の範囲では、プロフィール切替器と保存失敗状態は設計・要件に沿っており、UX上の指摘事項はありません。既存の設計ノートは変更していません。

## 確認した証拠

- `publishing-profiles/impl/clean-editor.png`: サイドバー上部に `Profile` と選択中の `プロフィール 1` があり、本文の編集領域を保ったままプロフィールを識別できます。
- `publishing-profiles/impl/dropdown.png`: 現在の選択にチェックが付き、`個人発信` を選べます。`Rename…` と `New profile` は選択肢より下に置かれ、主な切替操作を妨げません。
- `publishing-profiles/impl/save-failed.png`: 切替メニューを開いた状態でも `プロフィール 1` が選択中と分かります。`Could not save. Your text is kept on this computer.` と `Save again` は設計ノートの文言どおりで、失敗理由と次の操作を示しています。入力内容も残っています。
- 併記された操作観察では、未保存変更から切替後、元プロフィールに戻って記事を再度開いても入力文が保持されました。失敗時はプロフィール選択が変わらず、入力が保持されました。

失敗時の画像内に見える `[save-switch-fail-check]` は本文中のテスト用入力と判断しました（文字数表示は 101 / 280）。アプリの別の診断表示とは扱っていません。

## 受け入れ条件のレビュー

| 条件 | 判定 | 根拠・範囲 |
|---|---|---|
| 1. サイドバーのプロフィール表示・選択 | 表示部分は満たす | 画面上部のラベル、選択名、メニュー内の候補を確認。初期移行・改名・新規作成フロー全体は今回の画像では未確認。 |
| 2. プロフィール間のデータ分離 | 未確認 | 記事本文の保持は観察できたが、Voice・元にした文章・方針・言葉の雲を含む分離は画像から判定できない。 |
| 3. 再起動後の選択復元 | 未確認 | 再起動を含む証拠なし。 |
| 4. 保存成功後の切替と内容保持 | 部分的に確認 | 戻って記事を開いた際の本文保持は観察済み。サーバ保存完了を待ってから切り替えたことは、提示証拠だけでは独立に確認できない。 |
| 5. 保存失敗時に切替を止め、本文を保持 | UX上満たす | 失敗表示・再試行、選択中のプロフィール、本文保持を画像と観察で確認。 |
| 6. キュー結果の所有プロフィール固定 | 未確認 | キュー実行中の証拠なし。 |
| 7. 単一ログインと再起動後の選択 | 未確認 | ログイン数・再起動を含む証拠なし。 |

## 残る検証範囲

これは提示されたモック画像と操作観察に基づくUXレビューです。保存成功時のサーバー応答順序、プロフィール別データ分離、再起動復元、キュー所有者固定は画面だけでは保証できず、実装テストで確認してください。
