- **環境**: macOS 26.3.0 / Codex CLI 0.154.0 / Rust 1.92.0 / auth_mode = chatgpt

## 結論

**設計の前提は成立します。** Rust から Codex CLI を起動し、JSON Schema に適合した型付き出力を受け取れることを、実際の2タスクで確認しました。ただし**体験に関わる制約が2つ**見つかったので、UI 設計の前に扱いを決める必要があります。

## 見つかった制約

### 制約1: トークンストリーミングがない

`--json` で得られるイベントは**4種類だけ**でした。

```
thread.started → turn.started → item.completed → turn.completed
```

`codex exec` の全フラグを確認しましたが、delta / streaming 系のオプションは**存在しません**。`--output-schema` を使うと、答えは最後に `item.completed` として一括で届きます。

**影響**: 生成中に本文が流れる UI は作れません。出せるのはステージ表示（「生成中…」＋経過秒数）だけです。

### 制約2: 生成が遅い

| タスク | 所要時間 | 最初のイベント |
| --- | --- | --- |
| Voice 抽出（8メッセージ） | 45.6 秒 | 0.8 秒 |
| X ポスト生成 | 26.6 秒 | 0.1 秒 |

**影響**: ブリーフを入れてから原稿が出るまで**約30秒の無音**です。制約1と合わせると、その間ユーザーに見せられるものがありません。「一言入れたら原稿が出てくる」という体験の魅力を、この待ち時間が削ります。

考えられる打ち手（未決定）:

- 待ち時間を価値に変える — 1回の待ちで複数案を並列生成して選ばせる
- `--model` で速いモデルを指定できるようにする（未計測）
- 素直に受け入れ、経過時間と進行段階を丁寧に見せる

### 制約3: スキーマに description がないと粒度がずれる

`first_person` は一人称（「僕」など）を1語で入れる想定でしたが、モデルは段落で説明を書きました。JSON Schema の各フィールドに **`description` を必ず書く**必要があります。型だけでは意図は伝わりません。

## 生成された成果物（抜粋）

Voice 抽出は実用的な精度でした。`avg_sentence_length_chars: 21`、`uses_emoji: true` のような機械的な特徴に加えて、「機能そのものより受け手にとっての価値を重視する」といった癖まで拾えています。

そのプロファイルで書かせた X ポスト:

> v2公開しました🎉
> v1を使っている方へ。移行は5分もかかりません。結局はここだけ覚えてもらえれば大丈夫です。ざっと試して、気になる点があれば教えてください。反応見ながら直します。

サンプルにあった「結局は」「ざっと」「反応見ながら」を拾っており、**文体プロファイルが契約として機能する**ことは確認できました。90文字、140文字制限内です。

## 次に決めるべきこと

1. **30秒の待ち時間をどう扱うか**（制約1と2に対する product の答え）
2. Voice スキーマの確定 — 今回の出力を叩き台に、各フィールドへ description を付けて固める
3. 未ログイン・利用上限の実地再現（文字列マッチ以外の判定手段があるか）
