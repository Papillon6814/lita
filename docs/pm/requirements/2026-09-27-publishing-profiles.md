# 複数の発信プロフィールを切り替える

## 目的

一つの Google ログインで、発信先ごとに文章・文体・記事・編集方針を混ぜずに管理できるようにします。プロフィールを切り替えても未保存の編集内容を失わず、処理中のキューは元のプロフィールの記事に結果を保存し続けます。

## 利用者の状況

本人一人が同じログインで複数の発信先を運用する。現在はログインしたユーザーに紐づく Voice、その元にした文章、記事・版、キュー、および `user_settings` の編集方針・言葉の雲が一組だけあり、発信先ごとに切り離せない。画面は `Shell` と `Sidebar`、記事一覧・エディタ・文体・題決めの3柱で構成される。

## 必須

1. 一つの Google ログインの下に複数プロフィールを作成・選択できる。サイドバー最上部に常時見える切替器を置き、ラベルは日本語「プロフィール」／英語「Profile」。選択中の名前が分かり、切替器からプロフィールを選ぶ。既存データを持つ利用者には初期プロフィールを自動作成し、本人が名前を変更できる。初期プロフィール以外を作成するときは、作成前に他プロフィールと区別できる説明的な名前の入力を必須とする。
2. 各プロフィールは独立した Voice とその元にした文章、記事と全バージョン、記事の Voice 参照、キュー、編集方針、言葉の雲を所有する。プロフィールを切り替えた画面では選択中のプロフィールのデータだけを表示・更新し、同じログイン配下でも混ざらない。プロフィールのデータは引き続き本人のログインユーザーに属し、他のユーザーへ共有・公開しない。
3. 切替後も選択中プロフィールが再起動後に復元される。プロフィール名・選択状態はユーザーの既存データと同じ所有者境界で保存する。ログイン／ログアウトの仕組みやアカウント数は増やさない。
4. 初回移行で既存データを一つの初期プロフィールに割り当て、内容を保持する。記事と全 `article_versions`、`voice_id` による記事と Voice の参照、Voice と元にした文章、キュー状態、編集方針、言葉の雲を欠落・重複・孤立させない。既存利用者が移行後に同じ記事・版・文体を開ける。
5. プロフィール切替時、編集中のタイトル・本文・ブリーフ等に未保存変更があれば、サーバ保存完了を確認してから切り替える。保存が失敗した場合は切替を止め、入力内容を保ち、失敗が分かる状態にする。保存完了前の切替で内容を黙って捨てない。
6. プロフィール A で開始した待機中・実行中キューはプロフィール A に所有され続け、切替後もアプリの既存のキュー実行条件に従って処理を継続する。生成結果・失敗状態は A の元記事にだけ記録し、プロフィール B の記事・Voice・設定を参照・変更しない。

## 任意

- プロフィールの削除やデータのエクスポート。
- プロフィール別の表示順・色・アイコン。

## やらないこと

- Google アカウントを複数ログインすること、プロフィールごとのログイン・認証情報。
- 公開・予約投稿、外部サービスへの投稿、プロフィール間のデータ共有・複製・移動。
- v0.2 の3柱（記事・エディタ・文体）を増やすこと、既存の生成契約・記事状態・Voice 学習の仕様変更。
- 既存データの破棄・リセットを伴う移行、移行後に既存記事の版履歴や Voice 参照を捨てること。
- キューをプロフィール切替時に停止・移動すること、プロフィール切替を理由に別プロフィールの結果として保存すること。
- Notion への更新。この文書作成時点では同期保留。

## 受け入れ条件

1. サイドバー最上部に「プロフィール」／「Profile」と選択中名が常時見え、別プロフィールを選ぶと画面のデータが選択先に切り替わる。初回移行で既存利用者にはプロフィールが自動作成され、その名前を変更できる。2つ目以降は説明的な識別名を入力しないと作成できず、作成後はその名前が切替器に表示される。
2. A と B に異なる Voice・元にした文章・記事・方針・雲を用意すると、A から B に切り替えても相互の一覧・設定に相手の内容が現れず、それぞれを編集して戻ると元の内容が残る。
3. 既存データを持つ単一プロフィール利用者を移行すると、初期プロフィールに既存 Voice と文章、記事、各記事の全版、記事から Voice への参照、キュー、編集方針、雲が保たれ、既存の画面で読み出せる。
4. エディタに変更を入力して保存処理中にプロフィール切替を要求すると、保存成功後に切り替わり、再度元プロフィールを選ぶと入力内容が残る。
5. エディタの保存に失敗した状態で切替を要求すると、プロフィールは切り替わらず入力内容が残り、既存の失敗表示・再試行が利用できる。
6. A の記事をキューに積んで生成開始後 B に切り替えると、A の記事だけが生成結果または失敗状態で更新され、B のデータは変わらない。A に戻ると処理状態と結果が確認できる。
7. 既存の Google ログイン 1 つで複数プロフィールを利用でき、アプリ再起動後も最後に選択したプロフィールが選ばれている。

## 本人に聞かずに決めた既定値

| 項目 | 決めた値 | 理由 |
| --- | --- | --- |
| 初期プロフィール | 既存データの初回移行時に自動作成し、後から本人が名前を変更できる | 既存利用者を止めず移行しつつ、発信先に合う識別名を付けられるようにする（D-78） |
| 2つ目以降のプロフィール | 作成前に、他と区別できる説明的な名前を利用者が入力する。名前なしでは作成しない | 自動連番は発信先を識別できず、誤った場所へ書くおそれがあるため（D-78） |
| 名前の検証 | 空白のみ不可、前後空白を除去 | 空の識別名を避け、入力を軽く保つ |
| 新規プロフィールの空状態 | 空のプロフィールを作り、既存の空状態・導線を表示 | 他プロフィールの内容を複製せず、3柱の現行導線を再利用する |
| アクティブ選択 | 最後に選んだプロフィールをサーバ側ユーザー設定に保存し、再起動時に復元 | 同じログイン・端末で自然に再開できる。プロフィール一覧先頭へ勝手に戻さない |
| キューの継続 | 各記事が持つプロフィール所有者を用いて既存の再開条件で継続 | 利用者が明示した要件。切替を処理の停止・所有者変更に結び付けない |
| 削除 | 今回はプロフィール削除なし | 誤削除と参照・履歴の破壊を避け、必要性が確定していない機能を足さない |

## 残る質問

なし。名前の作成時要件と初期プロフィールの変更可否は D-78 で確定。削除・データ共有は今回の範囲外。技術設計で所有境界・移行方式・保存完了の保証が現行バックエンド制約上実現できないと判明した場合は、実装範囲を変える前に確認する。

## lita-ux への引き継ぎ

サイドバー最上部のプロフィール切替器と「プロフィール / Profile」ラベルは本人が選択済みのため維持する。切替時の保存中・保存失敗、初期プロフィール作成後の空状態、複数プロフィールがある状態を設計する。`Shell.tsx` / `Sidebar.tsx` の既存構造、`Editor.tsx` と `useAutosave.ts` の保存状態、`ArticleList.tsx`・`VoiceSection`・`TopicPicker` の既存空状態を参考にする。正常時は静かに、内部ID・DB用語は画面に出さない。プロフィール間の違いを装飾で過剰に表現せず、既存の3柱と生成・編集動作は維持する。
