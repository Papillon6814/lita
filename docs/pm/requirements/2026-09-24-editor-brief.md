# 題だけ書けば、何を書くかは Lita が出す（考える量は廃止）

- 出所: 本人の言葉「考える量の調整は不要で、常にベストを求めたい」「あとは記事内容の提案をどのようにさせるか」（2026-09-24）。聞き取りで「エディタでブリーフを自分で書きたくない。題だけあれば、何を書くか（狙い・読者・要点）を Lita が提案し、直してから書かせたい」。画面の指摘「エディタ右の『Lita に書かせる』の余白が変」
- 関係する決定: D-24（**衝突。改訂の提案**）、D-44、D-45、D-51、D-61、D-62
- Issue: #97（ブリーフの提案）、#96（考える量の廃止）

> **D-24 と衝突。改訂の提案。** D-24 は「推論量はユーザーが選べる（速度重視 = low / 品質重視 = medium）」でした。本人の判断（2026-09-24）は「常にベスト」です。**推論量は high 固定にし、選択肢を画面から消す**形に D-24 を改訂してください。D-24 の理由（短文では差が見えないので本人に委ねる）は、実際に使った本人が「委ねられたくない」と答えた時点で役目を終えています。

## 目的

エディタで白紙のブリーフ欄を前に手が止まるのをなくします。題さえ書けば、何を書くかの下書き（狙い・読者・要点）が出てきて、本人は直すだけで「書く」まで行けるようにします。あわせて、毎回聞かれるのに答えが毎回同じだった「考える量」を画面から消します。

## 利用者の状況

本人（唯一の利用者、D-51）が、書きたい題を思いついてエディタを開きます。本文は Lita に書かせるつもりですが、そのためにまずブリーフを自分で書かないといけません。「何について、誰に向けて、何を持ち帰ってほしいか」を自分の言葉で書けるなら、記事も自分で書けます。ここが実質いちばん重い入力になっていて、書く前に止まります。

順番待ち（D-61）で作った記事にはブリーフが既に入っています。手で作った記事（D-62 の空の下書き）だけが空です。つまり本人は「まとめて積んだときは楽なのに、1 本だけ書こうとすると急に重い」という段差を踏んでいます。

同じ右の欄で、「考える量」は速く／丁寧にの二択が毎回出ますが、本人は常に丁寧にを選びます。選択肢があること自体が、毎回「これでいいのか」を考えさせています。

## 必須

1. エディタ右の欄のブリーフの近くに、**Lita にブリーフを提案させる操作が 1 つ**ある。押すと `suggest_brief(article_id)` を呼ぶ。
2. 提案は**題・編集方針・元にした文章・過去記事**を材料にする。題が同じでも毎回作り直す（使い捨て。保存しない）。
3. 提案の中身は**狙い・読者・要点を含む 2〜4 文の平文**。箇条書きにしない。編集方針の行（誰に／持ち帰ってほしいこと／題材／触れないこと）をそのまま貼り付けない。長さの指定や「調べない」の指定は提案文に含めない。
4. 提案はブリーフ欄に**そのまま書き込まれ、その場で直せる**。提案されたブリーフと手で書いたブリーフを、あとから見分ける印は付けない。
5. **題が空のときは提案の操作を押せない**。代わりに一文で「題を書くと、何を書くかを提案します」と伝える。題も一緒に作ることはしない（題を出すのは記事一覧の「題を出す」の仕事、D-61）。
6. **既にブリーフがあるときは、確認を出さずに置き換える**。ただし置き換えた直後に「前のブリーフに戻す」を出し、押せば元に戻る。ほかの操作をするか記事を離れると消える。
7. 置き換えるとき、**元のブリーフに長さの行（「長さ: …」）と調べない旨の行があれば、その 2 行は残す**（順番待ちで作られた記事のブリーフが該当、`brief_for`）。提案の 2〜4 文がその上に来る。
8. **提案中はブリーフ欄を触れなくし、待っていることが分かる表示を出す**。10〜20 秒かかるので、段階表示はしない（D-23。Codex は一括で返す）。**中止できる**。中止しても元のブリーフは変わらない。
9. **失敗したときはブリーフを変えず、平易な一文と次の行動を出す**（原則 7）。Codex 未ログイン・未インストール・設定ファイル破損は既存の判定と案内に乗る。
10. **「考える量」の欄を画面から消す**。生成は常に最大（high）で行う。エディタからも順番待ち（`enqueue_articles`）からも同じ。
11. 「考える量」に付随するものをすべて片づける: 文言 `write.effort` / `effort.fast` / `effort.quality` / `effort.fastHint` / `effort.qualityHint` / `effort.fastHintLong` / `effort.qualityHintLong`（ja / en 両方）、`localStorage` の `lita.effort`（読み書きをやめ、残っている値は起動時に消す）、`TopicPicker` での読み出し。
12. **待ち時間が伸びることを、書いている間に一文で伝える**。長文の出す先（note / Medium）では「長い記事は 1〜3 分ほどかかります」相当、短文では従来どおり静かにする。時間は目安として言い、内部の用語（推論量・high）は出さない。
13. **右の欄の余白を整える**。「版履歴」の行、「Lita に書かせる」の見出し、ブリーフ欄の間隔が、欄と欄の間隔と同じ尺度で並ぶ。新しいトークンは足さない（原則 8）。

## 任意

- 提案の操作を、ブリーフ欄が空のときだけ目立たせ、埋まっているときは薄いリンクにする。
- 提案が気に入らないときに、もう一度押して別案を出すことが分かる文言にする。
- 順番待ちで作られた記事のブリーフでも、提案で作り直せることが分かるようにする（必須 6・7 で動きは同じ）。

## やらないこと

- 題の提案（記事一覧の「題を出す」が担う、D-61）。エディタからそこへ導線を増やすこともしない。
- ブリーフの保存・使い回し・テンプレート化。提案は使い捨て。
- 提案と本文生成を一続きにすること（押したら本文まで書く）。本人は「直してから書かせたい」と言っている。
- 「ブリーフ」という語の改名（残る質問 1）。
- 推論量を別の場所（設定・詳細）に移すこと。選択肢は残さず消す。
- 生成の契約の変更（D-28 / D-29 / D-59）。渡すのは従来どおり。

## 受け入れ条件

1. 題だけ入れた空の下書きで提案を押すと、狙い・読者・要点の分かる 2〜4 文がブリーフ欄に入り、そのまま「書く」が押せる。
2. 題が空のとき、提案の操作は押せず、題を書けば提案できると一文で分かる。
3. ブリーフが入っている記事で提案を押すと、確認は出ずに置き換わり、「前のブリーフに戻す」で元に戻せる。
4. 順番待ちで作られた記事で提案を押すと、長さと「調べない」の行が残ったまま、上の文だけが入れ替わる。
5. 提案中はブリーフ欄が触れず、待っていることが分かり、中止できる。中止するとブリーフは押す前のまま。
6. エディタのどの場面にも「考える量」「速く」「丁寧に」が出てこない。長文の記事を書いている間は、時間がかかる旨の一文が出る。
7. 右の欄の上部（版履歴 → 見出し → ブリーフ欄）の余白が、他の欄と欄の間隔と揃っている。

## 本人に聞かずに決めた既定値

| 項目 | 決めた値 | 理由 |
| --- | --- | --- |
| 題が空のときの提案 | 押せない。題も一緒には作らない | 題を出す場所は既にある（D-61）。ここで二つ目を作ると入口が割れる |
| 既存ブリーフの上書き | 確認なしで置き換え、直後に「戻す」 | 原則 5（モーダルより行内、戻る道を一つ残す）。確認は 2 回目以降うるさい |
| 置き換えの単位 | 追記ではなく置き換え。ただし長さ・調べないの 2 行は残す | 追記は本人に「どっちを読むのか」を判断させる。順番待ち由来の制約（D-61）は落とさない |
| 提案の形 | 狙い・読者・要点を含む 2〜4 文の平文 | ブリーフ欄はもともと「1〜2 文で十分」の欄。構造化すると欄の性格が変わる |
| 提案の保存 | しない（ブリーフ欄に書いた結果が自動保存されるだけ） | 使い捨て。題の提案（D-61）と同じ扱い |
| 提案中の見せ方 | 段階表示なし。待っている表示 1 つと中止 | D-23。Codex は途中経過を返さない |
| 失敗時 | ブリーフは変えない。一文＋次の行動 | 原則 7。壊さないことを優先 |
| 推論量 | 常に high。エディタも順番待ちも同じ | 本人の「常にベストを求めたい」。場所で差を付けると、また選択の話に戻る |
| `lita.effort` の残骸 | 起動時に消す | 使わない鍵を残すと、次に読む人が生きていると思う |
| 待ち時間の伝え方 | 長文の出す先のときだけ一文。短文は静か | 原則 2（正常時は静か）。1〜3 分は「困るとき」に当たる |
| 提案の材料の範囲 | 過去記事は直近から数本。本文が空の記事は数に入れない | 本人の記事はまだ少ない。空の下書きを材料にしても何も足さない |

## 残る質問

1. 画面の語を「ブリーフ」のままにしますか。本人は「ブリーフを自分で書きたくない」と言うときにこの語を使っているので今回は変えない前提で進めますが、原則 1（一つの概念に一つの名前、仕組みの語を出さない）からは外れています。改名するなら別件で。

## lita-ux への引き継ぎ

- 触る場所は `src/components/Editor.tsx` の右の欄（`aside.assist`）と `src/i18n/ja.ts` / `en.ts`。`TopicPicker.tsx` は `lita.effort` の読み出しを落とすだけ。
- 主ボタンは画面に一つ（原則 3）。右の欄の主ボタンは「書く／書き直す」です。**提案の操作を主ボタンにしない**。ブリーフ欄に付く二次的な操作として置いてください。
- 「考える量」が消えた分、右の欄は ブリーフ → 文体 → 出す先 → 書く の 4 段になります。必須 13 の余白はここも含めて通しで見てください。
- 参考にすべき既存画面: 順番待ちの「叩き台を作る」（`TopicPicker.tsx` の編集方針、Lita が書いて本人が直す形が既にある）、`PasteBox` の行内の直し方、`ErrorNote` の失敗の見せ方。
- 提案中の表示は、既存の `write.generating`（回るしるし＋一文＋中止）と同じ作りにしてください。新しい待ち方を増やさない。
- 数字と内部の用語は出さない（原則 2、`docs/pm/2026-09-22-ux-rereview.md`）。「high」「推論量」「10〜20 秒」を文言に書かない。時間は必須 12 の一文だけ。
- Rust 側の `suggest_brief(article_id) -> String` と high 固定はコーディネーターが入れます。UI は文字列を受け取って欄に入れるところまで。
